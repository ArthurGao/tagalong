# CLAUDE.md — frontend (Next.js)

The global rules in the root `CLAUDE.md` and in `docs/DESIGN.md` §11 apply here too. This file adds frontend-specific conventions.

**Before any UI work, read `docs/UI-STYLE.md`.** The app has three surfaces, each with its own visual style:

- `public` — buyer pages, "market sign-up sheet" style
- `merchant` — `/dashboard`, "stall ledger" style
- `admin` — `/admin`, "control room" style, dark only

Each surface sets its own `data-surface` attribute and fonts in its route-group layout, and the shadcn/ui CSS variables are defined per surface in `globals.css`. Never hardcode colors, fonts or radii inside a component; use the tokens.

## Conventions

- **Design mobile-first.** Most buyers arrive from a phone via a shared link. Design for a 375px-wide screen first, and make tap targets at least 44px.
- **Call the API only via the typed client** in `lib/api/client.ts`. Never use hand-written fetch URLs or hand-written response types. After backend changes, run `pnpm gen:api` from the repo root.
- **Use relative API paths** (`/api/v1/...`) so that the Next rewrite keeps everything same-origin and the cookies work.
- **Server Components by default.** Use `"use client"` only for interactive parts: forms, the option picker, polling.
- **Data fetching:**
  - Public listing pages are fetched server-side, with `revalidate: 10`.
  - The remaining-count and participant list refresh on the client every 15s, using TanStack Query with `refetchInterval`.
- **Forms:** use react-hook-form with zod. Validation mirrors the backend DTOs, but the backend is the authority. Show backend error `code`s using the i18n mapping.
- **Money:** display it only via `formatCents`, never by dividing inline. Price inputs are typed in dollars and converted with `dollarsToCents()` (string arithmetic) / `centsToDollarsInput()` in `lib/money.ts`.
- **Times in inputs:** `datetime-local` values are Auckland wall-clock time. Display with `isoToNzInput()`; save with `instantForInput(original, input)` from `lib/time.ts`, which keeps an untouched value at its original instant and returns null for a time skipped by daylight saving (show `listings.timeInvalid`). A repeated autumn hour resolves to the earlier instant.
- **Listing edits** send the `revision` they loaded and `reset()` the form from the response (new rows get their ids); `LISTING_STALE` means reload. Never compute totals for submission; the backend computes them. A display-only subtotal is fine.
- **Checkout:**
  - The `POST /public/listings/:shortCode/orders` request returns a `checkoutUrl`; redirect to it with `window.location.href = checkoutUrl`.
  - Handle `SOLD_OUT` by refreshing the options and showing a toast.
  - Generate an `Idempotency-Key` (UUID) when the buyer form mounts, send it on every submit of that form, and regenerate only after a successful response.
  - After returning from Stripe with `paid=1`, the order page polls `GET /public/orders/:code` every 2 s for up to 60 s while the status is `PENDING_PAYMENT`, showing a "confirming payment" state. It never shows "unpaid" during that window.
  - Implemented in `components/public/OrderSheet.tsx`, opened from `StickyBuyBar` (paid listings).
    - The key is held in `useState` for the life of the form.
    - `SOLD_OUT` invalidates the live listing query.
    - Redirects go through `lib/navigate.ts` `goTo()`, so tests can mock them.
  - The order page is `app/[locale]/(public)/o/[publicCode]` with `components/public/OrderView.tsx` (noindex, dynamic).
  - Free registrations use the same `OrderSheet`. `DynamicFields` + `answers.ts` (mirror of the backend rules) render the custom fields; attendee fields repeat once per place.
  - `Turnstile.tsx` loads Cloudflare's widget (test site key when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is empty). Tokens are single-use, so it is remounted (new `key`) after every submission. Tests mock it.
  - Merchant registration list: `dashboard/(app)/listings/[id]/orders` with `components/merchant/OrderList.tsx`.
    - Actions follow the backend's `canFulfil` / `canCancel` / `canNoShow` / `refundableCents`.
    - The refund dialog takes dollars (`dollarsToCents`), and there is a plain CSV link.
    - A refund Stripe has not confirmed yet shows as in progress (`pendingRefundCents`), and one that failed for good as `lastRefundFailed`; the refund request itself does not fail when Stripe is slow.
  - `components/merchant/CancelListing.tsx` (in PublishStep) reloads the preview on every open and cannot confirm without it, needs a reason and the exact title, and then polls the batch refund's progress.
  - Free listings get `{ kind: 'confirmed', publicCode, accessToken }`. Navigate to `/o/{publicCode}?t={accessToken}`, which shows "报名成功" (registered). Branch on `kind`, never on price.
  - Handle `ALREADY_REGISTERED` by showing "该邮箱已报名，确认邮件已重新发送" (this email is already registered; the confirmation email has been resent).
  - Every public order form includes the Cloudflare Turnstile widget, and its token is sent with the request.
- **Custom form fields:**
  - `components/public/DynamicFields` renders a listing's `formFields`. Attendee-scope fields repeat once per quantity.
  - The zod schema is built at runtime from `formFields`.
  - The merchant-side editor is `components/merchant/FormFieldBuilder`: add, reorder and delete fields, with at most 10.
- **WeChat:** `WeChatBanner` (in the public layout) renders when the UA contains `MicroMessenger`: a persistent top banner that explains Apple Pay is unavailable and shows how to open in the browser, plus a copy-link button. The UA is read with `useSyncExternalStore` (false on the server), so cached HTML stays shared.
- **Public footer** (`PublicFooter`, in the public layout): find-my-orders link and the language switch. `/find-order` (`FindOrderForm`) always shows the same message after a successful submit.
- **Language switch:** `LocaleSwitch` (one per surface; logic in `lib/locale-switch.ts`) swaps the locale segment and keeps the query string (the order token), in the real `href` too (read with `useSyncExternalStore`, empty on the server), so a new tab or a copied link keeps it. Public: footer; merchant: dashboard and auth layouts.
- **Merchant page** `/m/[slug]`: SSR, `revalidate: 60`, always noindex; `MerchantListings` renders the cards. The listing page's seller name links to it.
- **Share text:** `lib/share-text.ts` builds the group-chat message from `ListingSummaryDto.share` with `listings.share.*` strings; `ShareTextButton` (published rows in `ListingRows`) copies it with this site's origin.
- **Calendar:** `OrderView` shows "add to calendar" when `hasCalendar`; it fetches `calendar.ics` with the token header and saves it through `lib/download.ts`.
- **Robots:** `[locale]/layout.tsx` sets `robots: { index: false, follow: false }` for every page; a page opts in with `{ index: true, follow: true }`: the landing page (and legal pages, M9), and a listing whose `indexable` is true. New routes are therefore private by default.
- **Error codes:** `lib/api/errors.ts` maps every code in DESIGN §17 to an i18n key. An unknown code falls back to `errors.INTERNAL`; don't invent codes on the frontend.
- **Free vs paid copy:**
  - Button labels, list titles and the fulfil/check-in wording come from i18n keys selected by `listing.pricing`.
  - Never hardcode "接龙" (sign-up) or "报名" (register) inside components.
- **i18n:** every user-facing string lives in `messages/*.json`, in both locales. Merchant-entered content is shown as written.
- **OG images:** `l/[shortCode]/opengraph-image.tsx` shows the title, price range, remaining count and merchant name. This matters for WhatsApp, Facebook and Messenger previews.
  - Satori has no CJK glyphs: `lib/og-font.ts` fetches a Noto Sans SC subset of just the characters used (Google Fonts `text=`, cached a day, skipped for Latin-only text). This is server-side rendering, not a web font, so it doesn't break the no-CJK-web-fonts rule.
  - Colours come from `lib/surface-tokens.ts`; a test keeps it equal to `globals.css`.
- **Live listing data:** `components/public/live-listing.tsx` seeds TanStack Query from the SSR data (`staleTime` 15 s, so no refetch on mount).
  - The listing polls every 15 s while OPEN / NOT_YET_OPEN / SOLD_OUT, every 60 s when CLOSED / SUSPENDED / TAKEN_DOWN (all reversible), and stops only when CANCELLED. The sheet polls only in the live states and follows the live `showParticipants`.
  - `lib/api/public.ts` returns null only for 404 and throws otherwise, so SSR shows an error instead of a false 404 and a failed poll keeps the last data.
  - Polling queries use `retry: false`: the next tick is the retry.
  - `AvailabilityGate` owns the availability notices from live data: it swaps the whole page for the notice as soon as polling sees `TAKEN_DOWN`, and while the polled availability differs from the server-rendered one it calls `router.refresh()` (again every 11 s, since the 10 s ISR copy can be stale once), so server-rendered parts follow a takedown, restore, suspend or reopen.
  - Anything on the public page that depends on availability belongs in a live client component (`ListingTimeLine`, `StickyBuyBar`, …), not in the server page.
- **Privacy:** the frontend never receives buyer PII on public pages, so don't add fields for it. The order page requires the `t` token.
- **Accessibility:** use semantic HTML, give inputs labels, and keep contrast at WCAG AA. shadcn/ui defaults are fine.
- Generic UI pieces go in `components/ui`, and only shadcn/ui-generated components live there. Write feature components by hand.
  - `ui/dialog.tsx` is adapted from shadcn:
    - it portals into the page's `[data-surface]` element, so surface tokens and fonts apply;
    - it uses an inline close icon (no lucide-react) and a `closeLabel` prop (i18n).
  - The current shadcn registry imports `cn` from an npm package `cn`; use `@/lib/utils` instead.
  - When a second portaled primitive arrives (popover, select, toast), replace the `querySelector('[data-surface]')` lookup with a `SurfaceRoot` that renders the surface element and provides it through context to every portal.
- **Surface isolation:** `components/public`, `components/merchant` and `components/admin` must never import from each other. They may only share `components/ui` and `lib`. Enforced by ESLint `import/no-restricted-paths` in `eslint.config.mjs`, which checks the resolved file, so `@/` aliases and any relative path are covered.
- **Fonts:** load them with `next/font/google` in the surface's layout only. For CJK text, use the system font stack from UI-STYLE.md; never load web CJK fonts.
- **Mobile-first applies to public and merchant.** Admin is desktop-first (≥1280px) and only needs to degrade gracefully on smaller screens.
- **Host routing in `proxy.ts` runs before next-intl:**
  - On `ADMIN_HOST`: rewrite `/x` to `/{locale}/admin/x`. `/api/*` passes through; any non-admin page path returns 404.
  - On the main host: any `/admin` path returns 404.
  - Unit-test this function.
- **Auth uses Clerk (`@clerk/nextjs`) for both merchants and admins**, with one Clerk application:
  - **Provider placement:** put `<ClerkProvider>` in the layouts for `login`, `sign-up`, `dashboard` and `admin`. Public buyer pages must not load Clerk.
  - **Proxy (middleware):** `proxy.ts` uses `clerkMiddleware`, and inside it runs host routing, then next-intl.
    - On the main host: call `auth.protect()` for `/dashboard`.
    - On the admin host: protect everything except `/admin/login`. If `sessionClaims.metadata.role !== 'admin'`, rewrite to 404.
    - These checks are for UX only; the backend is the authority.
  - **Styling:** each surface passes its own `appearance` mapped to its CSS variables (merchant: light; admin: dark). Localization uses `@clerk/localizations` by locale.
  - **Admin login:** hide the sign-up footer link with `appearance.elements.footerAction: { display: 'none' }`. There is no admin sign-up route.
  - **API calls:** they are same-origin via rewrites, so Clerk's `__session` cookie reaches the backend. Don't add Authorization headers in the web app.
  - **Role checks in components:** read the role via `useUser().user.publicMetadata.role` or `sessionClaims` only for showing or hiding UI. Never use it to decide what data to fetch.
- **Admin pages:** every destructive action uses `ConfirmWithReason`, which requires a reason and asks the user to type the merchant slug. PII is shown via `MaskedPii`, which calls the reveal endpoint.

## Testing

- Component tests: Vitest + Testing Library in jsdom (`// @vitest-environment jsdom` at the top of the file), with `NextIntlClientProvider` + `messages/en.json` and the API client mocked (`vi.mock('@/lib/api/client')`). Examples: `components/merchant/ProfileForm.test.tsx`, `StripeButtons.test.tsx`. Planned: OptionPicker quantity limits, sold-out states, the masking display.
- Client components write through `useSave()` (`lib/api/use-save.ts`): it maps the error `code` (and network failures → `errors.INTERNAL`) to messages, exposes `code` / `details`, and never leaves a button stuck.
- Component tests render with `renderWithIntl` and build listings with `listingFixture` from `src/test/render.tsx`.
- e2e: Playwright, mobile viewport. The flow is: open listing → choose option → fill buyer form → (mocked) checkout redirect → order page.
